# API Request Findings

Reusable API request patterns that have produced findings. Product/tech + the request + what it reveals. **Client-agnostic**: record the generic pattern only; client URLs/data stay in `targets/<eng>/`. When you meet the same tech again, replay from here.

`impact`: what a positive result means. `auth`: what auth (if any) the request needs.

| product/tech | endpoint | method | request / payload | auth | reveals / impact |
|--------------|----------|--------|-------------------|------|------------------|
| Supabase | `/rest/v1/<table>` | GET | header `apikey:<anon>` | anon key | reads rows if no RLS policy -> data exposure |
| Supabase | `/auth/v1/signup` | POST | `{email,password}` | none | open registration; check `user_metadata` for priv-esc |
| GraphQL | `/graphql` | POST | introspection query `{__schema{types{name}}}` | varies | full schema -> hidden mutations/fields |
| Strapi | `/admin/init` | GET | - | none | reveals if admin not yet provisioned (takeover) |
| Elasticsearch | `/_cat/indices` | GET | - | none (pre-8) | index list -> data dump via `/_search` |
| InfluxDB 1.x | `/query?q=SHOW+DATABASES` | GET | - | often none | DB enum; `/query?q=` arbitrary InfluxQL |
| Actuator (Spring) | `/actuator/env`, `/actuator/heapdump` | GET | - | often none | secrets/creds in env or heap |
| Swagger / OpenAPI | `/swagger.json`, `/openapi.json`, `/v3/api-docs` | GET | - | none | full endpoint map -> hidden APIs |
| L5-Swagger (Laravel) | `/docs?api-docs.json`, `/api/documentation`, `/docs/asset/*` | GET | - | none by default | full OpenAPI spec of an otherwise undocumented API: operation list, path params, and which ops are writes (`PATCH /clients/{id}`, `DELETE /delete-invoice`). Publishing the spec alone is INFO, but it hands you the whole BOLA/BFLA test matrix |
| any calendar / schedule widget | the widget's own AJAX source (`events`, `availability`, `occupancy`, `busy-slots`) | GET | replay the exact params the page sends, then remove the scope flag | usually none | booking/appointment endpoints routinely serialise the whole `booking -> contract -> user` graph (name, e-mail, phone, payment state) while the page draws initials. Prime spot for unauthenticated mass PII |
| Joomla 4.0.0-4.2.7 | `/api/index.php/v1/config/application?public=true` | GET | needs `Accept: */*` (else 406 Not Acceptable) | none - CVE-2023-23752 | DB host/user/password + dbprefix; `/api/index.php/v1/users?public=true` leaks Super-User names/emails |
| ASP.NET Boilerplate / ASP.NET Zero | `/api/services/app/Account/ResetPasswordByEmailCallback`, `/api/services/app/Account/ResetPassword` | POST | `{"passwordResetCode":"<value>"}` alone, no `userId`, no email | none | stock ASP.NET Zero's reset endpoints take `userId`+`resetCode` together; when a deployment's DTO has been narrowed to the code alone, an invalid code returns a distinct 500 ("no such reset key") from a syntactically-accepted one, making the callback endpoint an unauthenticated code-VALIDITY oracle, and the same bare code on `ResetPassword` is sufficient to set a new password with no other identifier at all. Whenever you fingerprint ABP/ASP.NET Zero (the `/AbpUserConfiguration/GetAll` tell), diff the reset endpoints' actual required fields against the framework default rather than assuming the standard two-parameter contract still holds |
| Next.js (Pages Router only) | `/_next/static/<buildId>/_buildManifest.js` | GET | `<buildId>` is in any page's `__NEXT_DATA__` blob | none | the complete route table, including admin areas and pages linked from nowhere, with no wordlist and no fuzzing. Gotcha: App Router builds do NOT emit this file - establish which router you are on before reading its absence as "no hidden routes", or you will clear a surface you never actually enumerated (App Router already has its own route-existence oracle documented on this page) |
| Sentry (self-hosted) | `/auth/login/<org-slug>/` | GET | read the `window.__initialData` object out of the HTML | none | one unauth GET yields `version.current`, `version.build` (a full git SHA), `version.latest`, `upgradeAvailable`, the DSN (hence a project id), `distPrefix`, `singleOrganization` and `sentryMode`. The build SHA is the valuable part: it pins the exact upstream commit, so CVE triage becomes a diff of the commit range against upstream rather than guesswork, and preconditions like `singleOrganization:true` rule out multi-org advisories outright. Gotcha: when a Rust component (Relay) fronts some routes, its 401 body differs from the Django one - use that byte-level difference to tell which component answered before concluding anything about auth |
| Spring-WS (Java SOAP) | `/<ctx>/ws/<beanName>.wsdl` | GET | - | none | returns the WSDL only when `<beanName>` exactly matches a configured `WsdlDefinition` bean, and the match is CASE-SENSITIVE - the correct case returns the document, the wrong case returns 405 rather than 404. That asymmetry is a clean bean-name existence oracle, and the recovered document gives the real `targetNamespace` plus every operation and parameter type. With the true namespace you can then prove unauthenticated dispatch: a SOAP POST that reaches a NullPointerException executed, where a nonsense operation inside the SAME namespace returning an empty 404 is the control. Gotcha: an extensionless path sweep finds nothing here - probe the app's actual routing extensions |
| ASP.NET Boilerplate (ABP) / ASP.NET Zero | `/AbpUserConfiguration/GetAll` | GET | no params, no auth header | none | unauth dump of the whole app config: password policy (`RequiredLength`, each complexity toggle), EVERY permission name the product defines (`Pages.Users.Impersonation`, `*.ChangeStatus`, ...), feature flags and tenant settings. That permission list is the ready-made BFLA test matrix, and the password policy tells you the real minimum before any credential work. Tell: an Angular SPA whose XHRs carry `Abp.TenantId` or hit `/AbpUserConfiguration`. Gotcha: everything else on an ABP host commonly 401s cleanly, so this one open endpoint is easy to miss if you stop after the first few 401s |
| Ivanti/FrontRange HEAT ITSM | `/HEATSurveyProxy/SaaSSurvey.asmx` (SOAP, namespace `http://www.frontrange.com/WebSurvey/`) | POST | `AuthenticateAPI` with only `<userId>HEATadmin</userId><tenantId>&lt;tenant&gt;</tenantId>`, no password element (confirm via `?WSDL` first: the operation schema has no third field) | none | `AuthenticationStatus=Success` plus a live `SessionKey` and the backend SQL Server connection string, inline in the response. The session initially looks under-privileged; replay it against `SetRoleForUserSession(roleName="Admin")` on the sibling integration service to activate the role server-side before concluding access is limited. Try other vendor-default usernames (`FRSAdmin`, `Administrator`, `HSWAdmin`) too, a wrong one gets a uniform reject so this is not a username-enum oracle. Gotcha: a protective rule scoped to one HEAT SOAP directory is routinely not applied to a sibling directory on the same host, check every `.asmx` path independently |
| Directus | `/fields` | GET | - | none (anonymous role) | full field-level schema of every collection even where `/collections` and `/items/<c>` correctly 403 - the permission model covers the data endpoints but not the schema endpoint, so you can enumerate the entire data model through a closed door. Also audit `directus_files` and `directus_fields` for anonymous read; unrestricted `directus_files` lists and serves every stored document, including files not referenced by any published record. Gotcha: the REST and GraphQL API base is the HOST ROOT, not `/admin` - `/admin` is only the Vue admin SPA, so a scanner pointed there misses the entire API |
| Flowise (self-hosted LLM agent builder) | `/api/v1/version` | GET | - | none | exact version unauthenticated, which is the whole CVE triage for this product. Then map the auth middleware route by route: `leads`, `feedback`, `public-chatflows`, `prediction` and `get-upload-file` commonly sit OUTSIDE it - but every one is keyed by a chatflow UUID, so if that UUID is not recoverable from the client bundle, CT logs, archives or DNS, the surface is unreachable in practice and the honest verdict is "gated on an unobtainable id", not "vulnerable". Gotcha: test the case-manipulation auth bypass (request `/API/V1/chatflows` in altered case) before assuming the panel is gated, and check whether the version's known post-auth RCE needs credentials you do not have |
| Gravitee API Management | `/management/openapi.json`, `/build.json` | GET | - | none | exact product version plus the full management-plane OpenAPI spec (hundreds of paths) with no session. The portal plane (API catalogue, published specs, plans, entrypoints, owner e-mail) is unauth BY DESIGN, so it is rarely a finding on its own, but those published specs routinely name internal-only backend hostnames that are NXDOMAIN in public DNS - that is a ready-made SSRF target list reachable only from inside the gateway. Gotcha: the sensitive management operations still 401, so do not read the readable spec as a broken gateway; and check the `-tst` twin separately, its plans and registration settings are often looser |
| Ivanti Service Manager (HEAT ITSM) | `/<app>/Services/Session.asmx` | POST | SOAP `CheckSession()`, then `GetVersionInfo()`, with no cookie | none | unauth `BuildVersion=YYYY.R.0.YYYYMMDD`, `IsOnPremise`, `IsFedRamp` and the expected DB revision. Pin the patch band from this BEFORE claiming anything: a build below the fixed release puts the host in range, and `IsOnPremise=false` rules out on-premises-only advisories (treat that flag as an app config value, not proof of hosting). Tell: the root serves a ~1 KB meta-refresh to `./HEAT/Login.aspx`. Gotcha: an `.asmx` that 403s on a bare GET will still return its full operation contract at the same path with `?WSDL` appended |
| Moodle 4.x | `/lib/upgrade.txt`; `/lib/ajax/service-nologin.php` | GET; POST | POST body `[{"index":0,"methodname":"tool_mobile_get_public_config","args":{}}]` | none | the newest `=== X.Y.Z ===` section of `upgrade.txt` pins the deployed branch unauthenticated (cross-check the PHP floor in `/composer.json`); `tool_mobile_get_public_config` sits on the pre-auth allow-list and returns `registerauth`, `guestlogin`, `enablewebservices`, `authloginviaemail` and friends - the entire pre-auth surface in one call, so run it FIRST on any Moodle target. Gotcha: `/admin/environment.xml` ships forward-looking blocks describing the NEXT release, so a `<MOODLE version="4.1">` element inside it is not evidence you are on 4.1 |
| ArcGIS FeatureServer | `/<svc>/FeatureServer/<layer>/applyEdits`, `/deleteFeatures`, `/calculate` | POST | `deleteFeatures` with `where=OBJECTID=999999999` (matches no row) | none | the ERROR SHAPE is the oracle: `499 Token Required` = correctly gated; `400 ... not supported` = a read-only MapServer; `"Object is missing."` or `{"success":true}` with `updatedFeatureCount:0` = the edit engine ran unauthenticated, i.e. a `where=1=1` whole-table wipe primitive exists. This proves it while destroying nothing. Gotcha: layer ids are NOT contiguous, so enumerate the FeatureServer ROOT layer list - stopping at the first 404 badly understates the blast radius. Separately, an unauthenticated caller gets NO service-existence oracle: every guessed service name returns the same 499, so a wall of 499s is not a list of discovered services |
| Directus | `/server/info`, `/server/specs/graphql` | GET | - | none | `/server/info` is public by design and discloses `public_registration` and `public_registration_verify_email` - read it BEFORE spending any time on a self-registration privesc path, because it tells you outright whether that path is open and whether it needs a controlled mailbox. `/server/specs/graphql` serves the complete SDL unauthenticated on builds where `/server/specs/oas` returns 403, so a 403 on the OpenAPI spec is NOT evidence the schema is closed - always try the GraphQL spec route as well. Gotcha: version is deliberately hidden from anonymous callers here, so `/server/info` will not give you one |
| Claris FileMaker Server | `/fmi/data/v2/databases` | GET | - | none | lists every hosted database by name when the Admin Console option "Filter databases in Client Application" has been disabled. That setting is ENABLED by default, and disabling it simultaneously opens the Data API endpoint above, the WebDirect launch centre and the FileMaker Go client list - so check all three and report them as one configuration defect. Because the vendor documents the setting and its default, you can cite their own hardening guidance and score it as a customer misconfiguration rather than a product bug, which matters when a bounty programme excludes third-party product defects. Gotcha: the Admin API v2 endpoints stay correctly gated (error 1705), so a clean negative there says nothing about the Data API |
| PanteraCRM (vendor UAB Lexita) | `/{zone}/{module}/{action}` | GET | probe the zone-scoped path, e.g. `/system/dev/core`, never the bare `/dev` | none | version comes free from the `build <NNN.NN.N>` string in the login-page footer, and the `pan_ses<zone>` cookies name the zones. Routing is ZONE-prefixed, so every published advisory path probed at the web root 404s and looks patched - re-test each one under its real zone before recording a negative. Response shapes: ~2.8 KB 404 = no route; 302 to the login = route exists and is gated; 500 = handler reached. Gotcha: sibling deployments of this product drift across builds, and a route correctly gated on one instance is unauthenticated on another, so never carry a verdict between instances even when the vendor and bundle are identical |
| PHPRunner (Xlinesoft) | the login page's guest-login control | GET/POST | click or follow the guest-login control, no credentials | none | issues a genuine `runnerSession` cookie and a real redirect into the app rather than a demo or read-only shell. Map exactly what the guest role can reach (list/search/view actions) versus what it cannot (`_add`/`_edit`/`_export`/`_print`/`admin_*` typically still redirect back to login), since PHPRunner's generated access control is usually sound server-side and the guest session is a scoping question rather than an authorization bypass by itself. Tell: cookie name `runnerSession`, a `loginTName` JS variable naming the underlying table, and `showDetailedError`/`twoFactorAuth` config visible in page source |
| Redmine | `/plugin_assets/<plugin_name>/*?<unix-timestamp>` | GET | - | none | even with `login_required` enforced on every core controller (`/`, `/projects`, `/issues`, `/users`, `/activity`...), asset paths for installed plugins stay reachable pre-auth and name every plugin verbatim; the query string is a cache-busting Unix timestamp dating the plugin's last install/update. Read the page source for `plugin_assets/` references before assuming a login-gated Redmine has no enumerable surface; a plugin here (e.g. a clipboard/image-paste helper) can inject its own upload fields directly into the unauthenticated login page. Gotcha: `robots.txt` on a locked-down Redmine is commonly `Disallow: /`, which suppresses crawler discovery of this path without actually protecting it |
| Go Vocal (formerly CitizenLab) | `/web_api/v1/mentions/users?mention=<letter>&limit=<n>` | GET | - | none | returns full user records (first/last/display name, avatar URL, locale, account-creation and registration timestamps) to an anonymous caller, while the canonical `/web_api/v1/users` and `/users/:id` correctly 401 for the SAME ids in the same session. `limit` is honoured up to the full match count, so one request enumerates the directory. Generic form worth carrying to any product: whenever a collection route is properly gated, test its typeahead / autocomplete / mention twin - the authorization filter is frequently applied only to the canonical route. Confirm the users are not public-by-design first (check their public post and comment counts) |
| Streamlit (and any config-returning app with no version string) | `/_stcore/host-config` | GET | - | none | no semver is exposed anywhere, but the FIELD SET is a usable lower bound: a key that upstream added in a dated pull request proves the build postdates that PR, which is frequently enough to rule an older CVE out with evidence instead of a guess. Generalises to any product that serves a JSON config but withholds its version - diff the returned key set against the upstream repository's history rather than hunting for a version banner. Gotcha: this only ever establishes a FLOOR, never a ceiling, so it can retire a CVE but cannot confirm one |
| Supabase / PostgREST | `/rest/v1/rpc/<fn>` | POST | the CORRECT parameter name with a deliberately wrong-TYPED value | anon key | tells you whether the anonymous role holds EXECUTE on the function WITHOUT executing it: Postgres checks the grant at plan time, before type coercion, so `42501 permission denied` means no grant and `22P02 invalid input syntax` means the grant exists and only the cast failed. Safe on side-effecting functions, because the body never runs either way. The fuzzy-match hint already documented on this page for table names also fires for RPC names, naming a real function. Gotcha: a wrong PARAMETER name falls through to a different error entirely, so fix the name first, then vary only the type |
| Composer-based PHP app (Laravel/Symfony/custom) | `/composer.json`, `/composer.lock`, `/vendor/composer/installed.json` | GET | - | none | discloses the declared AND actually-installed dependency set; `composer.lock` is the resolved/declared set and can be STALE relative to what is really deployed, `installed.json` reflects what is on disk right now so prefer it when version-gating a CVE - citing the lockfile alone can claim a vulnerable version that isn't actually running. `/vendor/` sitting under the webroot also means any future dependency that ships a directly-invocable PHP script (e.g. PHPUnit's `eval-stdin.php`) becomes RCE-reachable the moment it is installed |
| Angular SPA (generic) | `assets/appconfig*.json`, `assets/env*.json` (bundled runtime-config path referenced from `index.html` or the build manifest) | GET | - | none | when the API host itself gives no clues (empty response at `/`, every `/swagger`, `/openapi.json`, `/api-docs` guess 404s), the SPA's own shipped runtime-config file names the real `apiBaseUrl`/`remoteServiceBaseUrl`, since the client must read it to know where to call; the SPA is served from a different host/path than the API it targets |
| WordPress | `/wp-json/wp/v2/users` (blocked, 403/502) vs `/?rest_route=/wp/v2/users` (same handler) | GET | none | none | WordPress's query-string REST routing form is a live fallback for the pretty-permalink path, so a firewall/WAF rule written only against `/wp-json/*` is bypassed outright; the query form returns the full account list (display names + login slugs) even where the path form correctly 403s |
| Supabase / PostgREST | `/rest/v1/<bogus_table>` | GET | `apikey:<anon>` + `Authorization: Bearer <anon>` | anon key | **table-name enumeration even when the schema root is locked.** Modern Supabase returns 401 "Only the `service_role` API key can be used" on `/rest/v1/`, but a NONEXISTENT table returns `PGRST205` with `"hint":"Perhaps you meant the table 'public.<real_table>'"` -> fuzzy-match leaks real names. Seed with generic guesses, then follow each hint |
| Supabase / PostgREST | `/rest/v1/<table>?select=*` | GET | headers `Range: 0-0` + `Prefer: count=exact` | anon key | **proves table scale WITHOUT retrieving rows** (`Content-Range: 0-0/<total>`). The correct shape for enumeration limits: `*/0` = anon has SELECT but RLS returns nothing (RLS working); `0-0/<n>` with a row = RLS absent on that table -> data exposure. Judge the columns before calling it a finding: public reference data (venues, categories) is usually deliberately public |
| Supabase | `/auth/v1/settings` | GET | `apikey:<anon>` | anon key | read-only auth config: `disable_signup`, `mailer_autoconfirm`, enabled providers. Check BEFORE attempting signup-based privesc; `disable_signup:true` closes that path outright. NOTE `user_metadata` is user-writable by design, so injecting `role` at signup always "works" -- it is only a finding if the app authorizes off `user_metadata` instead of `app_metadata` or an RLS'd table |
| Next.js (App Router) | any path | GET | read the `x-matched-path` response header | none | **route-existence oracle**: real routes echo their own path, unrouted ones return `/_not-found`. Maps protected routes and unlinked pages without a wordlist. A middleware auth gate shows as a 3xx with NO `x-matched-path` |
| Next.js server actions | any page URL | POST | `Next-Action: <id>` + `Content-Type: text/plain;charset=UTF-8`, body = JSON array of args | none | server actions are publicly invocable endpoints. Recover IDs **with their function names** from the client chunks via `createServerReference("<id>", ..., "<fnName>")`. The ID keeps its leading `40` Flight prefix; stripping it returns "Server action not found". A foreign `Origin` header returning 500 means built-in server-action CSRF protection is active |
| Next.js server actions (**second registration form - a `createServerReference` grep MISSES these**) | any page URL | POST | same `Next-Action` invocation as the row above | none | Some App Router builds register actions as **`(0, a(NNNNN).$)("<40-hex-id>")`** with **no `createServerReference` string and no `40` Flight prefix** anywhere in the bundle. Grepping for `createServerReference` or for `"40[0-9a-f]{38,}"` returns ZERO on these builds while the actions are live and unauthenticated. **You only find them by READING the `app/page-*.js` and `app/layout-*.js` chunks in full.** Names come from the surrounding assignment (`let r={getPosts:s,getSortedPosts:(0,n.$)("<id>"),...}`) or from the `useFormState(<var>, ...)` call the variable is passed to. Confirmed live on a municipal Next.js portal 2026-08-06 |
| Next.js server actions bound via `useFormState` | any page URL | POST | multipart form fields alone are **not** enough | none | An action consumed as `useFormState(action, initialState)` takes `(prevState, formData)`. Invoking it with only the form fields (with or without the CAPTCHA field) returns **HTTP 500 with a Flight error digest**, which is an ENCODING failure, not an auth verdict. Do not read that 500 as "the action is protected" - it fails before any token check. Settle CAPTCHA-enforcement questions with a real browser submission, not this 500 |
## How to extend
When a request pattern yields a finding on an engagement, add the **generic** form here (product, endpoint shape, payload, impact). Strip client host/path specifics. Cross-link the relevant technique page (e.g. [[supabase-attacks]], [[graphql]]).
